Jak działa dostęp warunkowy i które kontrolki mają pierwszeństwo

Dostęp warunkowy chroni wydawanie tokenów. Zasady są oceniane po uwierzytelnieniu, przy logowaniu lub podczas użycia tokenu odświeżania do uzyskania nowego tokenu dostępu.

Kluczowa zasada

Blokada zawsze wygrywa

Wszystkie pasujące zasady są stosowane. Jeśli jedna z nich blokuje dostęp, pozostałe kontrolki nie zmienią tej decyzji.

Po blokadzie kontrolki są egzekwowane w tej kolejności:

  1. uwierzytelnianie wieloskładnikowe, czyli MFA,
  2. zasady ochrony aplikacji (MAM, APP App Protection Policy),
  3. zarządzane urządzenie, zgodne lub dołączone hybrydowo,
  4. kontrolki niestandardowe, w tym warunki użytkowania,
  5. kontrolki sesji, w tym ograniczenia aplikacji, kontrola aplikacji i czas życia tokenu.

Jak oceniane są zasady

Zasady nie mają ustalonej kolejności oceny. Obowiązują wszystkie zasady, których warunki są spełnione.

Token

Chroniony jest odbiorca tokenu

Pozycja „Aplikacje w chmurze” wskazuje zasób, dla którego aplikacja żąda tokenu. Przykładowo zasada dla Exchange Online z wymaganiem MFA wymusza MFA przy żądaniu tokenu dla Exchange Online.

Wiele zasad

Kontrolki łączą się

Jeśli kilka zasad pasuje do żądania, egzekwowane są kontrolki ze wszystkich tych zasad. Zasady Identity Protection są stosowane przed oceną dostępu warunkowego.

Dostęp do aplikacji a dostęp warunkowy

Przypisanie użytkownika daje mu dostęp do aplikacji, ale nie omija dodatkowych wymagań bezpieczeństwa.

1

Przypisz dostęp

Dostęp do aplikacji można udostępnić wszystkim użytkownikom albo wskazanym grupom. Przypisania określają, kto może korzystać z aplikacji.

2

Sprawdź warunki żądania

Jeśli żądanie obejmuje zasada dostępu warunkowego, użytkownik musi spełnić jej kontrolki, zanim token zostanie wydany.

Zaufane urządzenie i typ klienta

Samo zarejestrowanie urządzenia nie wystarcza do uznania go za zaufane.

Urządzenie

Kiedy urządzenie jest zaufane

Urządzenie musi być zarządzane i zarejestrowane w usłudze katalogowej. Powinno też być oznaczone jako zgodne przez obsługiwane rozwiązanie MDM, na przykład Intune, albo należeć do lokalnego środowiska Active Directory.

Aplikacja kliencka

Przeglądarka lub aplikacja

Klient poufny oraz aplikacja używająca SAML są traktowane jak przeglądarka. Klient publiczny jest traktowany jak aplikacja mobilna lub klasyczna.

Bardzo ważne

Nie ufaj bezwarunkowo ciągowi User Agent

Nie należy zakładać, że User Agent zawsze istnieje lub jest poprawny. Może go brakować, może być błędny albo celowo zmieniony.

Platforma urządzenia

Platforma jest rozpoznawana na podstawie User Agent, który występuje tylko w protokołach webowych.

Ryzyko

Nieznana platforma może ominąć zasady

Protokoły takie jak POP3 i SMTP mogą nie przekazywać User Agent. Jeśli zasady obejmują tylko rozpoznane platformy, żądanie z nierozpoznaną platformą może nie zostać objęte żadną zasadą.

Zalecenie

Obejmij także nieznane platformy

Utwórz zasadę dla wszystkich aplikacji w chmurze i zacznij od użytkowników testowych. Wyklucz znane platformy, aby objąć pozostałe, a następnie wymagaj MFA lub blokuj dostęp.

Rekomendacja 1sec.pl

Projektuj zasady z pełnym pokryciem

Nie ograniczaj ochrony wyłącznie do platform, które da się rozpoznać. Uwzględnij przypadki, w których platforma urządzenia jest nieznana, i monitoruj takie logowania.
